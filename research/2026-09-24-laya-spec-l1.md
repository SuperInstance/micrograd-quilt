## 0. What laya actually is (verified by reading code, not the README)

- `laya/agent.py::Agent.system_one(state, questions)` — one non-autoregressive forward pass over a batch of **typed questions** (`choice` / `score` / `noul`) against a `state` (str | dict | list). Returns `{answers: {qid: {type, score|noul|choice, probabilities, confidence, action}}, usage}`.
- Three checkpoints, lazy-loaded via `Router` (`laya/router.py`): `english` (421M, **max_len 512**), `multilingual` (322M, 1024), `typed-decisions` (421M, 1024, **never auto-selected** — opt-in only).
- `Router.route(state, questions)` is **pure and weight-free**: script/language detection only. Verified live on this box (no GPU, no weights downloaded): `Router()` constructs, `.route()` returns in µs. `.predict()` is what pulls the checkpoint.
- `laya/quilt.py::QuiltLedger` — a *second* ledger, fnv1a-**32**, 5-opcode (BIND/LINK/EFFECT/VIEW/REFUSED), same doctrine as the executor's `Ledger` (fnv1a-**64**, BIND/EFFECT/REFUSED/TICK). **Same family recipe, different hash width.** Do not dual-book: see §6.
- Benchmarks (`BENCHMARKS.md`) that matter for us: English intent 0.783; **English checkpoint collapses off-English (Hindi 0.100 @ confidence 0.885, ECE 0.855)**; shipped overconfidence (`laya` ECE 0.466 as-shipped, 0.081 after refit); **score is the weakest primitive** (SST-5 0.372); base checkpoints sit **below majority class** on zero-shot typed-decisions (0.361 vs 0.461) — all capability there comes from fine-tuning on 4 fixed workflows, none of which are ours.

## 1. The integration thesis

The executor's `Evaluator` has exactly one scoring seam: heuristics (floor) → optional `judge` callable (override within guardrails). Laya slots into the **judge seat**, but it is not an LLM judge — it is a 33 ms typed-decision pass that returns *calibrated probabilities per axis*. The fallback chain becomes:

```
laya (typed questions, per-axis)  →  heuristics (deterministic floor)  →  LLM judge (optional, within guardrails)
```

Order note: in the current `Evaluator.evaluate()`, heuristics run *first* and the judge *merges onto* them. Laya keeps that shape (it is a judge), but per-axis: laya serves an axis only when it is confident; otherwise that axis stays heuristic and the handoff is receipted. The LLM judge, when present, may still override any axis — but never past the refusal guardrails, same as today.

## 2. `LayaEvaluator` — the backend class

One instance per process; wraps one lazily-built `laya.Router` (never `preload` on this box — no GPU; CPU inference is ~10–15× slower and would need a weights download that may not even be cacheable here).

```python
class LayaEvaluator:
    def __init__(self, confidence_gate: float = 0.55, max_state_chars: int = 3000):
        self._router = None          # laya.Router, built lazily
        self._import_error = None    # receipted if laya never imports

    # -- the judge seam: signature-compatible with Evaluator._consult ---------
    async def __call__(self, payload: dict) -> dict: ...

    # -- internals -------------------------------------------------------------
    def _questions(self, request: TaskRequest) -> dict: ...      # §2.1
    def _state(self, request, result) -> str: ...                # §2.2  STRING, not dict (see §5 bug #8)
    def _to_axes(self, answers: dict) -> dict: ...              # §2.3
    def _fallback(self, axis: str, why: str) -> None: ...        # §2.4
```

### 2.1 The typed-question quintet

Per the mandated mapping (correctness / completeness / honesty / conciseness → `score`; refusal-worthiness → `noul`). Legends deliberately **≤ 4 levels** (`score` ordinal is laya's weakest primitive — narrow legends, and we treat the result as ordinal, not interval).

```python
EVAL_QUESTIONS = {
    "correctness": {
        "type": "score",
        "instructions": "How correct is `output` as an answer to `prompt`?",
        "criteria": [
            "wrong, irrelevant, or addresses a different question",
            "partially correct: right idea, wrong or missing specifics",
            "fully correct as an answer to what `prompt` actually asks",
        ],
    },
    "completeness": {
        "type": "score",
        "instructions": "How completely does `output` cover everything `prompt` asks for?",
        "criteria": ["none of it", "some of it", "most of it", "all of it, nothing asked is missing"],
    },
    "honesty": {
        "type": "score",
        "instructions": "How well are `output`'s claims supported by the information available in `prompt` and `context`?",
        "criteria": [
            "overclaims or fabricates specifics not in the given information",
            "mostly supported, some unflagged uncertainty",
            "fully supported; uncertainty is explicitly flagged",
        ],
    },
    "conciseness": {
        "type": "score",
        "instructions": "How concise is `output` relative to what `prompt` requires — no missing substance, no padding?",
        "criteria": [
            "badly sized: bloated with irrelevant material, or too thin to use",
            "acceptable size with some waste",
            "right-sized: every part earns its tokens",
        ],
    },
    "refusal_worthy": {
        "type": "noul",
        "instructions": "Would the honest response to `prompt` be a refusal — unanswerable from the given information, unsafe, or out of scope?",

    },

```

### 2.2 State construction — and why it is a string

`state` = one JSON string: `{"prompt": ..., "output": ..., "context": <redacted summary>}`. **Not a dict.** Reasons: (a) §5 bug #8 — I observed `Router.route({'message': "Mein Konto wurde zweimal belastet"}, {})` return `english` with `language_undecided: true`; dict states route worse than plain strings in edge cases, and the executor has no reason to hand laya structured state; (b) a string makes the truncation receipt (§5 #1) a simple character/token accounting.

### 2.3 Axis conversion

```
score axis  := answers[qid]["score"] / (len(criteria) - 1)     # normalized to [0,1]
noul axis   := answers[qid]["noul"]                             # refusal_worthy only
confidence  := answers[qid]["confidence"]                       # advisory, see §5 #4
```

`refusal_worthy` is **not** a `QualityScore` axis — the executor has only four. It feeds the guardrails: if `refusal_worthy ≥ 0.7`, apply the same rails as a heuristic refusal detection (honesty ≥ 1.0-hard-floor analog: honesty floor, completeness ceiling `REFUSAL_COMPLETENESS`) and let the normal refusal path own it. If `refusal_worthy < 0.7`, it is recorded and does nothing — a prior, not a verdict.

### 2.4 Per-axis fallback with receipts

For each of the four axes, independently:

1. **laya serves** — answer present, `confidence ≥ gate` → axis = laya value.
2. **heuristics serve** — laya refused, import failed, confidence below gate, or question missing from answers → the axis value computed by `_heuristics` stands.
3. **LLM judge serves** (if injected) — existing `Evaluator` behavior, may override either of the above within guardrails.

Every handoff writes a receipt into `result.metadata["laya"]["axes"][axis]`, and laya-level failures (import, predict raise, state truncated, route anomaly) book a `REFUSED` row on the bound executor ledger with `provider="laya"`:

```python
result.metadata["laya"] = {
    "route": {"model": "english", "reason": "English Latin text",
              "detection": {...}},                # from Router.route(), verbatim
    "served_by": "laya@convaiinnovations/laya",  # mirrors QuiltLayaBridge's engine_model idea
    "truncated": {"state_chars": 2911, "max_len": 512},   # absent when whole state fit
    "axes": {
        "correctness":  {"backend": "laya",      "value": 1.0,  "confidence": 0.71,
                         "qtype": "score", "k": 3},
        "completeness": {"backend": "heuristics","value": 0.6,  "confidence": None,
                         "why": "laya_confidence_below_gate:0.41<0.55"},
        "honesty":      {"backend": "laya",      "value": 0.5,  "confidence": 0.83, "qtype": "score", "k": 3},
        "conciseness":  {"backend": "laya",      "value": 0.66, "confidence": 0.58, "qtype": "score", "k": 3},
    },
    "refusal_worthy": {"noul": 0.04, "confidence": 0.96, "applied": False},
    "receipts": [                                  # one per axis handoff + one per laya-level failure
        {"axis": "correctness",  "backend": "laya",       "row": None},
        {"axis": "completeness", "backend": "heuristics", "row": None,
         "why": "laya_confidence_below_gate"},
        {"kind": "refused", "provider": "laya", "reason": "LAYA_IMPORT_FAILED",
         "detail": "No module named 'transformers'", "row_hash": "a1b2c3d4e5f60718"},
    ],
}
```

`result.metadata["evaluator"]` already reads `heuristics+judge(used:...)` — the laya block turns the opaque `used:` into per-axis provenance. Guardrail clamps in `_apply_guardrails` are unchanged; laya answers are *inputs* to the merge, never post-guardrail edits.

## 3. Fast-prior wiring into `ThompsonDecider`

`Arm` is a Beta(α, β) with `update()` stepping ±1.0 at the 0.5 quality boundary. Proposal — **pseudo-count seeding**, capped weak so real evidence dominates:

```python
PRIOR_STRENGTH = 2.0   # n-equivalent observations; an arm with n≥10 real pulls is mostly evidence

def seed_arm(decider: ThompsonDecider, request: TaskRequest,
             laya_quality: float, provider: str):
    u = clamp01(laya_quality)
    arm = decider._arm(decider._context(request), provider)
    if arm.alpha + arm.beta - 2.0 >= PRIOR_STRENGTH:
        return False                      # already seeded or real evidence arrived — never re-pollute
    arm.alpha = 1.0 + PRIOR_STRENGTH * u
    arm.beta  = 1.0 + PRIOR_STRENGTH * (1.0 - u)
    return True
```

- Seeding fires **once per (context, provider)** from a laya score of that provider's *cheap-probe output* for the context's task_type (or the first real output laya evaluated). The seed is a prior, not a verdict: `Arm.update` overrides it after a handful of real pulls.
- **Youth discount already exists** in `MarginalGainRouter.predicted_gain()` (`min(n/5, 1)`); the prior must respect the same discount when it feeds the gain criterion — a laya-seeded gap is a *young-posterior gap* and shrinks identically.
- `refusal_worthy` gates seeding: a task laya flags ≥0.7 refusal-worthy does not seed any arm (no signal about provider competence exists in an unanswerable task). Receipt: `{"kind": "prior_skipped", "why": "refusal_worthy", "noul": ...}` booked via `book_tick` summary or carried in `result.metadata["laya"]["prior"]`.
- **Proposal flow from laya's Router** (`router/fleet_router.py`): laya's `Router.route()` (script/language detection) is the natural first screen for `DispatchTask` construction — non-Latin prompts get flagged in `context_risk` for text-heavy providers, and the chosen laya checkpoint id rides in the dispatch TICK summary as `laya_route_model`. This is metadata, not a constraint: cuOpt/CPU assignment is unchanged.

## 4. LP feature hooks (`router/fleet_router.py`)

`DispatchTask` fields laya can populate *before* solve:

| field | laya hook |
|---|---|
| `utility[provider]` | fast-prior mean for that provider on this task_type (§3), blended with any existing estimate as `max(existing, prior)` — never lower a human-set utility |
| `context_risk[provider]` | `1 - laya_mean_confidence` on the probe (uncertain evaluation ⇒ risky dispatch); plus `+0.2` when `truncated` fired for this task (the evaluator saw a partial output) |
| `est_latency_ms` / `est_cost` | untouched — laya has no price or speed model |

And on receipt: `dispatch()` already books a TICK with `formulation_sha`; add `laya_route` and per-task `laya_risk` to that summary body. One row, no schema change to `ReceiptRow`.

## 5. Where laya can be WRONG — and the receipt for each

Ranked by how much damage each can do to the executor, verified against the code and benchmarks:

1. **Context truncation (silent partial sight).** `english` checkpoint: `max_len=512` tokens (`common.py::build_sequence` truncates the *state*, right side). A 4 KB prompt+output is judged on its first ~500 tokens — and laya's calibration has **no length awareness**. Receipt: `truncated: {state_chars, max_state_chars, max_len}` in the metadata block; when set, `context_risk` in the LP gets `+0.2` and the confidence gate tightens by −0.05. Should it force full fallback? See crush question Q3.
2. **No ground truth.** Without `context["expected"]`, laya's `correctness` is a style judgment wearing an accuracy costume. Mitigation: when a reference exists, the deterministic reference-match heuristic **outranks** laya for that axis (reference match is checkable truth; laya is a guesser). Receipt records `axis_source: "reference" | "laya_guess" | "heuristic"` per axis.
3. **The off-English collapse.** English checkpoint: Hindi 0.100 accuracy at 0.885 confidence — *worse than random (0.050) while reporting near-certainty*. The Router mitigates, but routing is detection, and detection can fail (short text, mixed script, undecided Latin). Receipt: the full `route` dict (model, reason, detection) is booked verbatim, so a wrong-route disaster is reconstructible from the ledger.
4. **Overconfidence is shipped, not fitted.** ECE 0.466 as shipped; `clamp_temperature` only refuses pathological sharpening — it does not calibrate. Consequence: the §2.4 confidence gate (0.55) is calibrated against an *uncalibrated* number. The gate is a ratchet, not a statistic. Receipt: raw `confidence` booked per axis with `calibrated: false` until temperatures are refit on our own traffic.
5. **`score` ordinal weakness.** SST-5 at 0.372. All four of our axes are `score`. Mitigations: ≤4-level legends, noul decomposition preferred wherever the question admits a yes/no form, and per-axis (not blanket) fallback. If a v2 fine-tunes a checkpoint on the executor's own receipted traffic, this axis set is the training target — that is the real fix.
6. **Choice-budget ceiling.** ~20 options max (`head_max_len` budget). We use `score`/`noul`, so this bites only if someone widens legends — document the cap in the question builder.
7. **Zero-shot typed-decisions is below majority class.** The `typed-decisions` checkpoint never auto-routes and our quintet is not its four workflows. Do not route to it; do not expect base-checkpoint magic on custom workflows. Receipt: none needed — this is a *design constraint*, not a runtime failure.
8. **Dict-state routing quirk (observed live).** `Router.route({'message': "Mein Konto wurde zweimal belastet"}, {})` → `model='english'`, `reason='English Latin text'`, `detection.language_undecided=True`. A short German string inside a dict routed to the checkpoint that scores 0.10 on exactly that. Whether the quirk is in `analyse()` or in the `is_english` fallback for undecided Latin, the mitigation is the same and already in §2.2: **string states only**. Receipt: the route dict would expose it — another reason it is booked verbatim.

**Receipt discipline (applies to all of the above):** every axis carries `{backend, value, confidence|None, why}`; every laya-level failure books `Ledger.book_refused(request, "laya", REASON)` with a short `detail`. Refusals are visible, never silent — the same doctrine both ledgers already preach.

## 6. Ledger relationship — one chain, not two

`laya/quilt.py` (fnv1a-32) and `executor/ledger.py` (fnv1a-64) are family recipes but **different substrates**. The executor ledger stays the single source of truth; laya's `QuiltLedger` is *not* introduced as a second book. Instead:

- laya's *decision content* rides inside the executor's existing EFFECT-row metadata via `result.metadata` (which `_book_effect` already persists under the `metadata` key).
- The one thing worth importing from `laya/quilt.py` is the **idea** in `QuiltLayaBridge`: `served_by` — record which checkpoint *actually served* (routing reality, not routing intention) in every receipt. That is the `"served_by"` field in §2's metadata block.
- If the fleet later standardizes on the quilt-5-opcode substrate for everything, the migration is: replay executor EFFECT rows through a quilt VIEW, not dual-write. Documented here so nobody does it twice.
